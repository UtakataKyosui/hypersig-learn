# 実機・本番Cronの受け入れ手順（#11・#31・#34・#78）

この文書は実施準備であり、結果は未実施。対象は#79、仕様は#1。過去の自動試験結果は [受け入れ記録](mvp-acceptance.md)、設定は [README](../README.md)を参照する。実機表示とPushサービス受付を別々に判定する。

## 開始条件

- 運用担当者が対象環境と試験時間を決め、本人のアカウント・端末を使用する。試験用の薬は実際の服薬と混同しない名称にする。
- 対象変更をレビューし、承認されたCIで配布する。手元からデプロイしない。run URL・配布SHA・migration結果・smoke test結果を記録する。
- HTTPS、Googleログイン、既存D1 binding、毎分Cron設定、VAPID設定を確認する。秘密の値を表示・転記しない。既存VAPID鍵を再生成しない。
- iPhoneは対応iOSのSafariでホーム画面へ追加してアイコンから起動する。AndroidはPush対応ブラウザを使う。端末・OS・ブラウザの版、起動形態、端末timezone、日時（JST／UTC）を記録する。

## 本番Cron（#34）

1. DashboardのWorker `app`で、配布SHAとCron `* * * * *` を確認する。設定変更はこの確認作業に含めない。
2. Observability → Logsでscheduled実行を確認する。必要なら `npm ci` 後に `npx --no-install wrangler tail app` を使う。数分間の連続する自然起動を記録し、HTTP手動呼出しやローカルCronと区別する。`scheduled: notification failure`／cleanup failureの有無も記録する。
3. 通知設定で購読を保存し、テスト通知を予約する。ページ・SSEを閉じ、`push_probe_result` のoutcomeと端末表示を別欄に記録する。acceptedはPush受付のみ。ログがなければ受付を推定しない。
4. 通常の服薬枠を現在より数分先のJST時刻に保存し、アプリを閉じる。通知表示・タップ復帰を確認する。通常配信は現在結果ログを出さないため、必要ならDashboardのD1 consoleで次の集計だけを確認する。薬名・document・endpoint・鍵・cookieは取得しない。他の配信も集計に含まれるため、これだけで特定端末の成功とは判定しない。

```sql
SELECT j.state AS job_state, d.state AS delivery_state,
       d.last_error_class, COUNT(*) AS count
FROM notification_jobs j
JOIN notification_deliveries d ON d.job_id = j.id
WHERE j.scheduled_at_utc >= (unixepoch('now') - 1800) * 1000
GROUP BY j.state, d.state, d.last_error_class;
```

`sent`はサービス受付を保存した状態で、服薬済み・端末表示済みではない。Cron起動だけではVAPIDや実配信の成功としない。`--subject-only` の確認が必要な場合は、担当者が連絡先変更の承認を得て既存手順で行い、公開鍵を維持したこととCI結果を記録する。今回は未実施。

## 端末シナリオ（#11・#78・#31）

| ID | 操作 | 期待結果 |
|---|---|---|
| D1 | 未許可→拒否、設定から許可、購読保存、解除→再登録 | 許可・保存・失効を区別。片側失敗後も再読込／再設定で復旧 |
| D2 | テスト予約後に画面を閉じる。通常予定でも繰り返す | SSEなしでOS通知。薬名・量を含まず、タップで当日の予定へ。起動中windowと未起動の両方を試す |
| D3 | 新規保存→枠2件（異なる時刻・小数量・独自単位）→再読込→編集・削除 | 保存後は編集URL。タイトルと保存内容が一致し、枠は時刻順。タッチ・キーボード操作が可能 |
| D4 | 曜日未選択、空欄、逆転期間、重複休薬を送信 | 対応するエラーと入力保持。曜日エラーを日曜だけの誤りとしない |
| D5 | 日付・時刻picker、数値入力、下端入力・保存・削除dialogを操作 | 拡大やキーボードで操作不能にならず、横スクロールなし。Safariとホーム画面でそれぞれ記録 |
| D6 | 端末timezoneをUTC等へ変更し再起動 | 予定はAsia/Tokyoのまま。試験後は端末設定を元へ戻す |
| D7 | 入力中に通信断→保存→回復→再保存、認証期限切れ→ログイン | 通信エラー／401を区別し、入力を保持。回復後に保存できる |
| D8 | 未送信予定の編集・無効化・削除・休薬、休薬翌日の再開 | 旧予定を送らず、元の繰り返し基準で再開。送信開始後は撤回できない境界を記録 |
| D9 | 15分を超えて端末がオフライン→復帰、旧SWから更新 | 古い予定の一括配信なし。送信・通信・OS表示時刻を分ける。OS側の遅延はサーバー期限と区別 |

OSのバックグラウンド制限や省電力の状態も記録する。「画面を閉じた」「タスクから除いた」「OS設定で強制停止した」は異なる条件として記す。#11の成立性確認後、完成ビルドで#31を実施する。同じビルド・端末・条件の証拠は相互参照できる。
